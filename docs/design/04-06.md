## 4. Partitioning and skew

**Inputs.** 30,000 ev/s peak (§2). One partition = one consumer process applying batches of ≤ 200 in one transaction: **~1,700 ev/s measured** (STEP3 notes; D4 amended). Zipf(0.9) over 60,000 merchants, same weighting as the harness (`ledger_events.py:46`, `1/r^0.9`): **top-1 = 4.85 %, top-10 = 15.6 %, top-1 % = 46.2 %** (derived; the brief says ~40 %).

| Question | Answer | Working / mechanism |
|---|---|---|
| Partition count | **64** | 30,000 ÷ 1,700 ≈ 18 needed at uniform load. ×3.5 headroom for hash imbalance and hot keys; power of two; up to 64 consumers. |
| Key | `merchant_id` (= channel) | Per-merchant order is the correctness requirement: CAPTURE must see its AUTH open, REFUND its CAPTURE, PAYOUT_REQUEST the `available` produced by every earlier event (`rules.py`, mirroring `apply_event` L165–215). Key = merchant ⇒ one partition ⇒ one consumer ⇒ log order (D1). |
| Hottest merchant at peak | **1,455 ev/s** | 30,000 × 4.85 %. That is 86 % of a partition's ceiling *on its own*. With random hashing it shares the partition with ~1/64 of the rest (~450 ev/s), giving **~1,900 ev/s > 1,700**. |
| Mitigation 1 (now) | **Pin the top-N merchants** to dedicated partitions | Custom partitioner: a small `hot_merchants → partition` table (top 32 by trailing 7-day volume); everyone else hashes over the remaining 32. The top merchant then runs alone at 1,455/1,700. |
| Mitigation 2 | Raise the per-partition ceiling | Batch cost is O(distinct rows), not O(events) (`pg_ledger_store.py:3-12`); batch 500 → ‹M4›. |
| One merchant exceeds a **worker's** throughput | Nothing splits; lag grows on that partition only | A worker is one process per partition, so a worker limit is a partition limit. Other merchants on other partitions are unaffected (they only share a partition with the hot one if not pinned, see mitigation 1). `consumer_partition_lag{partition}` alarms; the backlog lives in the broker (§3). |
| If one merchant still exceeds a partition | **Don't split the merchant** (it breaks the ordering above) | (a) a faster consumer for that partition; (b) let lag absorb the peak and catch up off-peak; (c) redesign: split by capture chain, with PAYOUT_REQUESTs serialised separately. |

**Beyond one session (> 25,000 frames/s).** 30,000 > 25,000 per session (§2) ⇒ ≥ 2 sessions; we plan for all 16 `client_id`s (≈ 1,900 frames/s each at peak, room for a 13× hot spot).

| Concern | Mechanism |
|---|---|
| Channel → `client_id` | Rendezvous hash of `merchant_id` over 16 ids (adding an id moves ~1/16 of channels); `channel_owner(channel, client_id, version)` in Postgres; each LOGON subscribes to its subset (§2). |
| One live session per `client_id` | One leader lock per id: `leader_lock.name = client_id` (the table is already keyed by `name`, `models.py` `LeaderLock`; D12). Each id gets its own reader pair. |
| Fencing per `client_id` | `session_lease` is one row today (`singleton = 1`) → key it by `client_id`; messages carry `client_id` (`LedgerMessage` v2, D16) so the stale-epoch check (D21) compares against the right row. |
| Reassigning a channel without two owners | **Checkpointed handoff:** (1) bump `channel_owner.version` and mark the channel `draining`; (2) the old session stops granting CREDIT for it (no new frames arrive) and waits until its acked seq = `channel_progress.last_seq`; (3) flip the owner to the new `client_id`; (4) the new session includes the channel in its next LOGON with `resume = channel_progress.last_seq` (D14). Overlap is harmless anyway: the contiguity CAS (`channel_progress.last_seq = seq − 1`) accepts each seq once whichever session sent it. |
| **Reassignment on failure** (a session's leader dies) | Channels **don't move** on a reader failure: the `client_id`'s standby takes `leader_lock[client_id]` (8.5 s measured handover), logs on with a larger epoch, claims `session_lease[client_id]`, and resumes the same channel subset from `channel_progress` (D14). The gateway allows one live session per `client_id`, so the old session is superseded (`gateway.py:380-385`); a paused old leader is fenced exactly as in §2. Only if **all** replicas of a `client_id` stay down past an SLA (e.g. 60 s) does the assignment move: the coordinator bumps `channel_owner.version` and reassigns the channels to surviving ids. The dead id can't be holding them because its lease has expired and its epoch is stale. The new owners resume from `channel_progress`, and the contiguity CAS makes any late frame from the dead session a duplicate. |

## 5. PostgreSQL at 3 B rows

Sized at the brief's **3 B rows** (§2) ≈ 36 M rows/month over 84 months; the note at the end covers what our per-event history really produces.

### 5.1 Schema, partitioning strategy and keys

| Table | Rows | Partitioning | Keys / indexes | Why |
|---|---|---|---|---|
| `ledger_history` | 3 B / 84 ≈ **36 M per month** | **RANGE (event_time), monthly** → 84 online partitions | PK `(merchant_id, seq, event_time)` (the partition key must be in the PK); index `(merchant_id, event_time DESC)` per partition (`ix_ledger_history_merchant_time`) | `as_of` prunes to one month; old months detach to cheaper storage with no DELETE |
| `merchant_month_open` (new) | 60 k/month | RANGE monthly | PK `(merchant_id, month)` | Opening balance per merchant per month, so an `as_of` before a merchant's first event of the month never walks back to earlier partitions |
| `processed_events` | 15 M/day | **RANGE (applied_at), daily**, drop after 7 days | PK `(event_id, applied_at)`; `ix_processed_events_applied_at` | Only needed inside the replay horizon (gateway 72 h + margin). Partitioning makes the PK per-partition, so a redelivery on a later day isn't caught by it; it *is* caught by the contiguity CAS on `channel_progress` (seq ≤ `last_seq` ⇒ duplicate, `pg_ledger_store.py` `_classify`), which is the real cross-day guard (D4, D22) |
| `merchants`, `channel_progress`, `platform_fees`, `payouts` | 60 k / 60 k / ≤ 64×currencies / 40 k/day | none (payouts: monthly once > 100 M) | — | Small, hot, updated in place |

### 5.2 The index that serves an exact `as_of` in < 200 ms, and its write cost

**Index:** `ix_ledger_history_merchant_time (merchant_id, event_time DESC)`, local to each monthly partition. Each row stores the balance *after* that event (D8), so the answer is one row, with no summing.
**Query:** `WHERE merchant_id = $1 AND event_time <= $2 ORDER BY event_time DESC LIMIT 1` (`pg_read_store.py` `balance_as_of`). Partition pruning picks the month of `$2`. If that merchant has no event ≤ `$2` in that month, one PK lookup in `merchant_month_open` returns the opening balance. At most 2 index descents per query.
**Measured** at 2 M rows: `Limit → Index Scan using ix_ledger_history_merchant_time`, **0.05–0.08 ms** execution, HTTP p99 6.2–9.3 ms (STEP4 notes). **At 36 M rows/partition** (fan-out ~250): 3 → 4 B-tree levels, +1 page read, < 1 ms warm, a few ms cold. **Well inside 200 ms at any instant in 7 years.**
**Write cost it adds:** one extra B-tree insert per event, on top of the heap and PK inserts. Per merchant, keys arrive in time order, so inserts land on right-most leaf pages (few splits, hot in cache). Bytes: ‹M2: index bytes/row›; WAL share: part of ‹M1›.

### 5.3 Update-heavy rows: HOT, vacuum, bloat, contention at 30 k ev/s

| Row | Update pattern | Contention | Bloat control |
|---|---|---|---|
| `merchants` (60 k) | once per batch per merchant (bulk write-back, `pg_ledger_store.py` `finish`) | none: a merchant lives in one partition ⇒ one writer | No indexed column changes ⇒ **HOT** updates; `fillfactor = 70` so the new version fits on the same page; `autovacuum_vacuum_scale_factor = 0.01` |
| `channel_progress` (60 k) | once per batch per channel (CAS) | none (same reason) | HOT, `fillfactor = 70`, same autovacuum |
| `platform_fees` | once per batch per currency | **none: sharded `(currency, shard = partition)` (D9)**; one writer per shard | 64 × currencies rows; trivial |
| `payouts` | 3–6 transitions per payout | rows owned by one executor lease (D27) | partial index `ix_payouts_claimable` keeps terminal rows out of the hot index |

**Contention at 30 k ev/s is zero by construction:** each merchant, channel and fee shard has exactly one writer (its partition's consumer), and batches turn ~200 events into one row update per merchant. Row locks are only ever contended during a rebalance (§6).

### 5.4 WAL per day

WAL per applied event: **‹M1: WAL bytes/event›** (measured on an isolated instance by `pg_current_wal_lsn()` difference over a known number of events). **WAL/day = ‹M1› × 15 M ≈ ‹M1×15M›** at steady state; **‹M1› × 30,000/s ≈ ‹M1×30k›/s** at peak. `wal_compression = on` (`docker-compose.yml`) reduces full-page images after checkpoints.

### 5.5 `synchronous_commit` and `fsync`

`synchronous_commit = on`, `fsync = on` (`docker-compose.yml`). The broker offset is committed **after** the Postgres commit (D4). If an acknowledged commit were lost (async commit + crash), the offset would already say "done" and the events would never be re-applied: a silent hole, which breaks exactly-once. Batching (D4) makes the fsync cost per batch (~200 events), not per event, so we don't need to trade durability for throughput. In production: one synchronous standby (`synchronous_standby_names = 'ANY 1 (…)'`) so a primary loss doesn't lose acknowledged commits (§8).

### 5.6 Connection pooling mode, and what it forbids

Today: direct connections, a small pool per process (consumer 2+1, reader 2+1, executor threads+2; `services/*/main.py`) ≈ 60 connections at full scale-out, under `max_connections = 200`. If a pooler is needed: **PgBouncer in session mode** only. Transaction mode forbids exactly what correctness relies on:

| Forbidden in transaction mode | Where it would bite | Incumbent defect |
|---|---|---|
| Session-level advisory locks | lock and unlock land on different server connections | **P7** (`payouts.py:51-57`) |
| `SET` without `LOCAL` (e.g. `statement_timeout`) | applies to a random server connection | **C13** (`ledger_consumer.py:30`) |
| Prepared statements reused across transactions | psycopg auto-prepare | — |
| `LISTEN/NOTIFY`, temp tables, `WITH HOLD` cursors | state lost between transactions | — |

Our row locks (`FOR UPDATE`, `SKIP LOCKED`) are taken and released inside one transaction, so they would survive transaction pooling. The rule is to keep it that way.

> **Note — the brief's 3 B vs its own event rate.** 450 M events/month × 84 months = **37.8 B events**. We write one `ledger_history` row per DATA frame (≈ 95 % of frames) ⇒ **~36 B rows**, 12× the brief's 3 B. The design above still holds at that size: ~430 M rows/partition is still 4 B-tree levels, so `as_of` stays sub-ms. Storage is what changes (‹M2› × 36 B). Options:
>
> | Option | Rows in 7 y | `as_of` exact? | Cost |
> |---|---|---|---|
> | A. Row per DATA event (current) | ~36 B | yes, one lookup | ‹M2› × 36 B on disk |
> | B. Row only when a balance changes (skip rejected/ignored) | ~29 B | yes | A − ~20 % |
> | C. Per-merchant snapshot every hour **or** every 1,000 events, whichever first, + replay from the snapshot | 60 k × 61 k h ≈ 3.7 B + 36 B ÷ 1,000 ≈ **3.7 B** (≈ the brief's 3 B); events in cold storage | yes: snapshot ≤ t, then replay ≤ 1,000 events of one merchant (the hottest does 194 ev/s ≈ 700 k/h, so an hourly-only snapshot would not bound it) | more code; replay of ≤ 1,000 rows in the p99 |
>
> We keep A (exact, measured, simplest); C is the move if storage becomes the constraint.

## 6. Isolation levels

No code sets an isolation level (`grep isolation services/` → none) ⇒ **READ COMMITTED everywhere**. RC is enough because every read-modify-write is either under a row lock or a compare-and-set:

| Transaction | Where | Level | What makes RC safe |
|---|---|---|---|
| Consumer batch | `pg_ledger_store.py` `apply_batch` | RC | `SELECT … FOR UPDATE` on `channel_progress` and `merchants` for every channel in the batch; on referenced `auths`/`captures`; CAS `UPDATE channel_progress … WHERE last_seq = :orig` else `BatchConflict` → rollback; `processed_events` PK |
| Executor claim | `pg_payout_repo.py` `claim` | RC | `FOR UPDATE OF p SKIP LOCKED`, row predicates repeated in the locking CTE so EvalPlanQual drops rows another claimer just leased (`pg_payout_repo.py:20-23`) |
| Executor transition / renew / release | `pg_payout_repo.py` | RC | single `UPDATE … WHERE payout_id AND lease_owner AND status AND attempt` (CAS, rowcount 1) |
| Token mint claim | `pg_token_store.py` | RC | single CAS `UPDATE bank_token … WHERE issued_at < now() − 5 s AND token = :seen` |
| Leader lock / fence | `pg_lock.py`, `pg_fence.py` | RC | `INSERT … ON CONFLICT DO UPDATE … WHERE expires_at < now() OR holder = …`; `UPDATE session_lease … WHERE epoch < :e` |
| API reads | `pg_read_store.py`, `pg_ops_store.py` | RC | single-statement reads; one consistent snapshot each |

**The anomaly at READ COMMITTED if we removed one lock and one constraint.** Removed: **`SELECT … FROM merchants … FOR UPDATE`** (`pg_ledger_store.py` `prepare`), and with it the **`channel_progress` CAS** (`UPDATE … WHERE last_seq = :orig`, `finish`). The batch reads each merchant's balance into memory and writes back **absolute values** (`ON CONFLICT DO UPDATE SET settled_minor = EXCLUDED.settled_minor`, `finish`). Two transactions touch the same merchant only during a **rebalance**: consumer A has had partition 7 revoked mid-batch but is still committing; consumer B is assigned partition 7, starts at the last committed offset, and so re-reads records A is about to commit. Anomaly: **lost update**.

| t | A (revoked, still finishing; batch = seq 101) | B (new owner; batch = seq 101–102) |
|---|---|---|
| 1 | reads M-42: `settled = 10,000`, `last_seq = 100` | |
| 2 | applies 101 CAPTURE (+5,000 − fee 175) → 14,825 in memory | reads M-42: `settled = 10,000`, `last_seq = 100` (A not committed; RC sees the old row) |
| 3 | writes `settled = 14,825`, `last_seq = 101`; **commits** | |
| 4 | | seq 101: `processed_events` insert conflicts → skipped as duplicate (correct) |
| 5 | | seq 102 PAYOUT 8,000 against its **stale** 10,000 → `settled = 2,000`; writes `settled = 2,000`, `last_seq = 102`; commits |
| result | **`settled = 2,000`; correct is 6,825.** A's CAPTURE (+4,825) is lost, although it is recorded in `processed_events` and will never be re-applied. | |

**With the lock (what runs):** at t2 B's `FOR UPDATE` blocks until A commits; RC then returns the committed row (14,825), and seq 102 yields 6,825.
**With the CAS but without the lock:** at t5 B's `UPDATE channel_progress … WHERE last_seq = 100` matches 0 rows (A set it to 101) → `BatchConflict` → B rolls back and retries from fresh state.
Either guard prevents the lost update. We keep both: the CAS also covers a brand-new merchant that has no row to lock yet.
